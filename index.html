Lección 1

Patrones de comportamiento y State

Las tres familias, qué es State y la confusión más común con Strategy.

Los tres tipos de patrones

FamiliaQué resuelveEjemplos
CreacionalCómo crear objetos sin acoplarse a clases concretasSingleton, Factory Method, Builder
EstructuralCómo componer clases y objetos en estructuras más grandesAdapter, Decorator, Proxy, Composite
ComportamientoCómo se comunican y reparten responsabilidadesState, Strategy, Observer, Command
Los patrones de comportamiento no hablan de cómo se construye el código, sino de cómo fluye la lógica de negocio.

Qué es State en una frase

State permite que un objeto cambie su comportamiento cuando su estado interno cambia. Parece que el objeto cambió de clase, pero en realidad delega en un objeto de estado diferente.

Analogía: una máquina expendedora. Es la misma máquina, pero su comportamiento depende de si tiene dinero insertado, si ya dispensó el producto, o si está sin dinero.

State vs Strategy — la confusión más común

AspectoStateStrategy
¿Quién decide?El objeto mismo, según su estado internoEl cliente, desde afuera
¿Cambia en ejecución?Sí, el objeto transita entre estadosGeneralmente no, el cliente lo fija
¿Cuándo usarlo?Comportamiento depende de estado que el objeto gestiona soloComportamiento lo elige el usuario o cliente

Lección 2

Anatomía de State

Los tres participantes, diagrama de clases y flujo de delegación.

Context

Context

Objeto principal. Mantiene referencia al estado actual y delega cada operación en él. Nunca contiene condicionales if estado == ...

State

State (interfaz)

Clase base abstracta. Declara los métodos comunes que todos los estados deben implementar (pagar(), enviar()).

ConcreteState

ConcreteState

Una clase por estado real (Pendiente, Pagado, Enviado). Implementa el comportamiento y, cuando corresponde, cambia el estado del Context.

Flujo de delegación: ¿quién hace qué?

AcciónQuién la ejecutaQué sucede
Usuario llama pedido.pagar()Pedido (Context)Delega en self.estado.pagar(self)
El estado actual decideConcreteStateEjecuta su lógica y, si corresponde, hace pedido.estado = OtroEstado()
Cambio de estadoConcreteState sobre PedidoEl Context apunta a un nuevo objeto estado. La próxima llamada usa el nuevo comportamiento.
✓ Úsalo si
  • Un objeto tiene un comportamiento que depende de su estado interno.
  • Tienes condicionales if estado == ... repetidos en varios métodos.
  • Vas a tener al menos 3 estados o la lógica va a crecer.
  • Quieres evitar tocar el Context al agregar estados nuevos.
✗ No lo uses si
  • Solo tienes 2 estados simples que nunca cambian.
  • El comportamiento lo elige el cliente desde afuera (usa Strategy).
  • Quieres evitar crear una clase por estado para algo trivial.

Lección 3

Implementación mínima en Python

Código copiable, probado y listo para ejecutar. Más el playground interactivo.

Código completo

Guárdalo como estado_pedido.py y ejecútalo con python estado_pedido.py

Python estado_pedido.py 
from __future__ import annotations
from abc import ABC, abstractmethod


# Interfaz State
class EstadoPedido(ABC):
    @abstractmethod
    def pagar(self, pedido: "Pedido") -> None: ...
    @abstractmethod
    def enviar(self, pedido: "Pedido") -> None: ...
    @abstractmethod
    def cancelar(self, pedido: "Pedido") -> None: ...


# ConcreteState: Pendiente
class Pendiente(EstadoPedido):
    def pagar(self, pedido):
        pedido.estado = Pagado()
        print("Pago aceptado. Pedido ahora está pagado.")

    def enviar(self, pedido):
        print("No se puede enviar: aún no se ha pagado.")

    def cancelar(self, pedido):
        pedido.estado = Cancelado()
        print("Pedido cancelado antes de pagar.")


# ConcreteState: Pagado
class Pagado(EstadoPedido):
    def pagar(self, pedido):
        print("El pedido ya está pagado.")

    def enviar(self, pedido):
        pedido.estado = Enviado()
        print("Pedido enviado al cliente.")

    def cancelar(self, pedido):
        print("No se puede cancelar: ya está pagado.")


# ConcreteState: Enviado
class Enviado(EstadoPedido):
    def pagar(self, pedido):
        print("Ya se envió. No se puede pagar.")

    def enviar(self, pedido):
        print("El pedido ya fue enviado.")

    def cancelar(self, pedido):
        print("No se puede cancelar un pedido ya enviado.")


# ConcreteState: Cancelado
class Cancelado(EstadoPedido):
    def pagar(self, pedido):
        print("El pedido está cancelado.")

    def enviar(self, pedido):
        print("El pedido está cancelado.")

    def cancelar(self, pedido):
        print("El pedido ya está cancelado.")


# Context
class Pedido:
    def __init__(self):
        self.estado: EstadoPedido = Pendiente()

    def pagar(self):   self.estado.pagar(self)
    def enviar(self):  self.estado.enviar(self)
    def cancelar(self): self.estado.cancelar(self)


if __name__ == "__main__":
    p = Pedido()
    p.pagar()    # → Pagado
    p.enviar()   # → Enviado
    p.pagar()    # → Bloqueado
    p.cancelar() # → Bloqueado

Lección 4

State vs Strategy

Dos patrones estructuralmente gemelos con propósitos e intenciones completamente diferentes.

Principio Fundamental

¿Quién decide el comportamiento?

A nivel de diagrama UML de clases, State y Strategy se ven casi idénticos: ambos tienen una clase principal que delega en una interfaz polimórfica con múltiples implementaciones concretas. Sin embargo, su intención y control de ciclo de vida son radicalmente opuestos:

State (El objeto decide)

El comportamiento depende del estado interno del objeto. El objeto cambia de estado autónomamente a medida que ocurren eventos en el sistema. El cliente exterior ni siquiera necesita saber qué estado concreto está activo.

Strategy (El cliente decide)

El cliente elige conscientemente un algoritmo desde afuera y se lo inyecta al contexto. La estrategia usualmente no cambia durante la vida del objeto, y las estrategias concretas son completamente independientes entre sí.

Matriz comparativa exhaustiva

Criterio de Decisión Patrón State Patrón Strategy
Intención principal Cambiar de comportamiento según el ciclo de vida interno. Intercambiar familias de algoritmos intercambiables.
¿Quién elige la implementación? El objeto o los propios estados concretos en las transiciones. El código cliente, pasándolo como argumento o inyección.
Mutación en tiempo de ejecución Alta frecuencia: transita dinámicamente de un estado a otro. Baja o nula: se fija al instanciar el contexto.
Conocimiento entre clases concretas Los ConcreteState suelen conocerse para disparar la transición al siguiente estado. Las ConcreteStrategy no se conocen entre sí ni tienen relación directa.
Referencia al Contexto Casi siempre reciben el contexto (self.estado.pagar(self)) para mutar su propiedad. Rara vez conocen al contexto; reciben solo los datos estrictamente necesarios para calcular.
Ejemplo clásico del mundo real Reproductor de música: Reproduciendo, Pausado, Detenido. Cálculo de impuestos: ImpuestoColombia, ImpuestoEspana, ImpuestoUSA.

¿Pueden combinarse en un mismo proyecto?

Sí, y es una práctica común de ingeniería. Cada patrón ataca una dimensión ortogonal del problema:

Python state_con_strategy.py 
# La estrategia de cálculo de envío la define el cliente (Strategy)
class EstrategiaEnvio(ABC):
    @abstractmethod
    def calcular_costo(self, peso_kg: float) -> float: ...

class EnvioAereoExpress(EstrategiaEnvio):
    def calcular_costo(self, peso_kg): return peso_kg * 25.0

# El ciclo de vida de la orden se gestiona internamente (State)
class OrdenCompra:
    def __init__(self, estrategia_envio: EstrategiaEnvio):
        self.estrategia = estrategia_envio  # Strategy inyectada desde afuera
        self.estado = Pendiente()           # State gestionado por el ciclo interno

Lección 5

State con Observer y Command

Cómo desacoplar notificaciones de eventos y construir máquinas de estados con historial reversible.

Combinación 1

State + Observer: Notificar transiciones sin acoplar módulos

Cuando un pedido cambia de estado a Pagado o Enviado, muchos subsistemas quieren enterarse: enviar un correo al comprador, emitir la factura electrónica y descontar stock del almacén. No pongas esa lógica dentro del estado concreto. Conecta el patrón Observer:

Python state_con_observer.py 
from abc import ABC, abstractmethod

class ObservadorEstado(ABC):
    @abstractmethod
    def en_cambio_estado(self, pedido_id: str, anterior: str, nuevo: str) -> None: ...

class ServicioEmail(ObservadorEstado):
    def en_cambio_estado(self, pedido_id, anterior, nuevo):
        print(f"[Notificación Email] Pedido {pedido_id}: {anterior} -> {nuevo}")

class ServicioInventario(ObservadorEstado):
    def en_cambio_estado(self, pedido_id, anterior, nuevo):
        if nuevo == "Pagado":
            print(f"[Inventario] Reservando stock físico para orden {pedido_id}")

class PedidoConEventos:
    def __init__(self, pedido_id: str):
        self.id = pedido_id
        self.estado = Pendiente()
        self._observadores: list[ObservadorEstado] = []

    def suscribir(self, obs: ObservadorEstado):
        self._observadores.append(obs)

    def cambiar_estado(self, nuevo_estado):
        anterior = type(self.estado).__name__
        self.estado = nuevo_estado
        nuevo = type(nuevo_estado).__name__
        for obs in self._observadores:
            obs.en_cambio_estado(self.id, anterior, nuevo)
Combinación 2

State + Command: Transiciones reversibles (Undo / Redo)

En aplicaciones complejas (editores de texto, flujos de aprobación o carritos de compra), los usuarios deben poder deshacer una transición de estado si hubo un error. Encapsular cada transición en un Command permite mantener una pila histórica de marcha atrás:

Python state_con_command.py 
class ComandoTransicion(ABC):
    @abstractmethod
    def ejecutar(self) -> None: ...
    @abstractmethod
    def deshacer(self) -> None: ...

class ComandoPagarPedido(ComandoTransicion):
    def __init__(self, pedido: Pedido):
        self.pedido = pedido
        self.estado_previo = None

    def ejecutar(self):
        self.estado_previo = self.pedido.estado
        self.pedido.pagar()

    def deshacer(self):
        if self.estado_previo:
            self.pedido.estado = self.estado_previo
            print(f"[Undo] Pedido restaurado a {type(self.estado_previo).__name__}")

Regla de simplicidad (KISS & YAGNI)

No sobre-ingenierices desde el día uno. Aplica esta regla de tres pasos para decidir si agregar patrones adicionales:

Nivel 1

Solo State

Si únicamente requieres que métodos cambien de comportamiento según la etapa del objeto sin efectos secundarios externos.

Nivel 2

State + Observer

Si otros servicios o interfaces de usuario deben reaccionar inmediatamente a los cambios de estado sin conocer la lógica de transición.

Nivel 3

State + Command

Si existe el requerimiento de auditoría de transiciones, ejecución diferida en colas o capacidad de revertir acciones erróneas.

Glosario de Patrones de Comportamiento

Definiciones concisas y precisas para tu sustentación académica y código productivo.

Término Definición y Rol en la Arquitectura
State (Patrón) Patrón de diseño de comportamiento que permite a un objeto alterar su comportamiento cuando su estado interno cambia, simulando un cambio dinámico de clase.
Context (Contexto) Clase principal que mantiene una referencia privada a una instancia de ConcreteState y delega en ella toda la lógica dependiente del estado.
State (Interfaz) Clase base abstracta que declara la firma de todos los métodos que representan acciones sensibles al estado (ej. pagar(), cancelar()).
ConcreteState Clases concretas que implementan el comportamiento asociado con un estado particular del Context y gestionan las transiciones válidas.
Transición de Estado El acto de reemplazar la instancia de estado activa en el Context por otra diferente en respuesta a una acción o estímulo.
FSM (Máquina de Estados) Modelo computacional compuesto por un número finito de estados, transiciones entre ellos y acciones asociadas a cada evento.
Strategy Patrón comportamental hermano donde el cliente elige desde afuera un algoritmo intercambiable que rara vez muta en tiempo de ejecución.
Observer Patrón comportamental que define una suscripción uno-a-muchos para notificar automáticamente a múltiples objetos ante un cambio de estado.
Command Patrón comportamental que transforma una solicitud en un objeto autónomo, facilitando historiales, colas de trabajo y operaciones reversibles (undo).
